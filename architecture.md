# Rust Monitor architecture

## Boundary

Rust owns Linux collection, TOML configuration, extension lifecycle, formatting, ThinkPad fan-control decisions/commands, read-only fan-level observation, and a diagnostic CLI. A thin GTK3 C adapter owns XFCE API 2.0 registration and widget lifecycle. The adapter preserves XFCE's registration macros instead of maintaining custom Rust bindings. The core is usable and testable without GTK development packages.

## Display and collection

The widget contains metrics, a smart-fan icon toggle, and the observed hardware fan level. Horizontal panels show inline text beside the toggle; vertical and deskbar panels stack metrics and the toggle. CPU temperature, first fan, and available RAM display their values and units without CPU, Fan 1, RAM, or available labels. The second fan by sorted sensor-path index is tooltip-only, even if the first fan is unreadable; later fan entries retain their existing labels. Tooltips retain all metric labels and readable fans. Tooltip text is plain text, never markup. Missing readings and failed scripts are hidden from the panel and described in the tooltip; an empty snapshot displays Monitor so diagnostics remain accessible. The fan level is a bare `0`–`7` or `auto` immediately beside the icon, or `?` when unavailable; it stays visible in full and RAM-only modes. Its label tooltip describes the current level or the unavailability reason and is separate from the toggle's smart-control tooltip.

Ordinary right-button presses on metrics toggle full display and RAM-only immediately from cached snapshots, independently per plugin instance. Full is the initial state; no selection is persisted. A child event box consumes the ordinary press before parent panel menu handling; Ctrl-modified clicks and the middle button propagate normally; ordinary left-click opens the fan temperature popup. Additional non-Ctrl double/triple button-3 events are consumed without toggling, since XFCE's parent handler would otherwise open its menu during rapid toggles. Polling and full tooltip details continue when minimized. RAM-only text is supplied explicitly by Rust, not parsed from display strings; absent memory uses Monitor. Minimized text is never CPU-colored; returning full restores the current snapshot's warning and layout.

CPU discovery uses the hottest tempN_input from coretemp, k10temp, zenpower, or cpu_thermal drivers, avoiding unrelated storage temperatures. Explicit sensor paths override discovery. Fan discovery covers all fanN_input files; zero RPM is a real reading. RAM means MemAvailable. Filesystem occupancy uses used/(used+available), reflecting unprivileged capacity rather than reserved blocks; / is the default and paths are configurable.

## Smart fan control

The icon toggle is opt-in, starts off per instance, is not persisted, and remains visible in RAM-only mode. Disabling or removing the plugin leaves the last fan level unchanged, including level 0: this is an explicit user choice, not a safe restoration guarantee. An already-started check may finish after disabling. Multiple instances are independent and do not coordinate access to the shared hardware; only one controller should be enabled.

Control uses the configured CPU sensor or the hottest recognized CPU reading, and reads `speed:` from `/proc/acpi/ibm/fan`, not the first displayed hwmon fan. This matches the RPM condition to the fan receiving commands. Raw CPU above the selected upper threshold requests `level auto`; CPU below the selected lower threshold AND RPM <2000 requests `level 0`; the default range is 58–60°C. All other cases preserve the level. Zero RPM is valid. Missing/invalid readings (including any discovered CPU read failure or negative CPU temperature), invalid configuration, and command errors attempt `level auto`, report the error and fallback outcome in the toggle tooltip and the popup error area, and retry while enabled. Metric collection still uses its existing tolerant missing-reading/default-config behavior.

Commands use fixed `/usr/bin/sudo -n /usr/bin/tee /proc/acpi/ibm/fan` argv and at most eleven bytes of fixed stdin, without a shell. They reuse the extension subprocess bounds/cleanup with a one-second timeout per attempt, including fallback. Password prompting is forbidden; permissions and kernel support are administrator-managed. No helper, sudoers rule, or kernel configuration is installed automatically by the plugin or build — a separate user-invoked script, `scripts/install-fan-sudoers.sh`, installs the scoped NOPASSWD rule (validated with `visudo -c`, rolled back on failure) when the administrator chooses to run it. Neither CLI collection nor ordinary metric collection performs control writes.

A separate one-at-a-time GTask checks immediately on enable and two seconds after each completion, independent of metric refresh and slow extensions. Generation tracking discards stale UI results after off/on transitions; disabling cancels the timer. Removal waits for all workers without requiring main-loop completion callbacks, then prevents future scheduling. Filesystem/device I/O remains unbounded; command failure plus fallback adds up to two seconds of subprocess timeout budget. The adapter draws a theme-colored fan glyph itself to avoid a missing icon on themes without a fan asset.

### Fan level observation

A read-only observer starts at construction, independently of smart control, and schedules one second after each completion. It launches one GTask at a time from the same worker/teardown synchronization as the other jobs, so removal cancels the timer and waits for an in-flight read before returning. It reads `/proc/acpi/ibm/fan`; it never writes hardware, invokes sudo or a fallback command, consults the toggle or last command, reloads configuration, or reports in the smart-control error area.

Observation accepts exactly one `level:` line. Only documented displayable values `0`–`7` and `auto` reach the label. Documented `disengaged` and `full-speed` states, missing/duplicate lines, and invalid values yield `?`; the label tooltip gives the diagnostic, without echoing arbitrary device text. Read errors also yield `?` with the path and OS error. The label refreshes on the GTK thread after each completion, continues while smart control is off, and changes neither the existing two-second control schedule nor leave-last-level-unchanged disable behavior.

### Temperature range popup

Left-click on metrics opens a separate GTK popup window in either view, without changing the fan toggle or metric view. Two integer sliders span 30–90°C; changing one clamps it to keep lower < upper with at least 1°C between them. Changes apply to the next fan job, which captures an immutable pair of thresholds at launch; an in-flight job may finish with the previous pair. Rust validates the pair again before any decision and attempts auto on invalid input, so GTK constraints are not the hardware boundary. The independent CPU display warning remains fixed at >80°C.

The popup carries no explanatory or success text: below the sliders it renders only current errors — the active fan-control failure (sensor/configuration/command) and any range load/save failure — each under a short header in a bounded scroll area hidden while both sources are healthy. A source clears when it recovers; disabling smart control clears its fan error immediately. Unrelated metric/disk/extension failures stay in the metric tooltip, not the popup.

Thresholds are per-instance UI state, so the adapter persists them through XFCE's instance rc API rather than changing shared sensor TOML. It loads `[SmartFan]` keys `off-celsius` and `auto-celsius` at construction and atomically replaces the local file on adjustment, preserving other valid keys/comments. Missing settings use defaults; unreadable, malformed, missing-key or out-of-range saved settings use defaults and surface a settings error in the popup. A save error retains session values and shows that error; the next adjustment retries and clears it on success. Malformed existing files are not overwritten. Manual rc edits are read only on instance startup; fan enablement is never persisted.

The adapter opens it with `xfce_panel_plugin_popup_window`, requiring XFCE panel >=4.19. That API handles positioning, autohide locking, input grabs, and menu-like outside-click/Escape dismissal. It must be a native toplevel, not a GtkPopover: external plugins live in panel-sized GtkPlug/XEmbed windows, so child popovers are clipped even when GTK reports them visible. Offscreen-only tests originally missed this boundary. Parent-window destruction hides the popup early; plugin removal hides and destroys it before waiting on workers. The replaced popover-specific focus/autohide machinery is not retained.

## Configuration contract

Instances share XDG_CONFIG_HOME/xfce4/panel/rust-monitor.toml, falling back to HOME/.config when XDG_CONFIG_HOME is missing or relative. Each collection reloads it, avoiding a settings dialog. Missing configuration uses defaults; invalid configuration rejects the whole file, uses defaults, and exposes a diagnostic. Poll delay defaults to two seconds and ranges from 1 to 3600 seconds.

## Extension contract

Trusted local executables run as argv arrays without an implicit shell. First stdout line is a nonempty value; optional second line is tooltip detail. Extra lines are ignored. Text must be UTF-8 without NUL/control characters except LF/tab. Combined stdout/stderr is capped at 4096 bytes; default timeout is 1000 ms, configurable from 10 to 10000 ms. At most 16 extensions run sequentially. Failures hide their metric and surface bounded diagnostics.

Nonblocking pipes prevent descendants holding pipes open from stalling collection. On success, failure, overflow, or timeout the process group is killed and the direct child reaped. This is cleanup, not sandboxing: deliberately detached descendants may escape it. Extensions must not daemonize.

## Native lifecycle and ownership

monitor_collect returns an owned C-compatible snapshot with full text, tooltip, and ram_text strings; monitor_snapshot_free releases it and all three strings exactly once. NULL config selects the shared default file; panics are contained at the ABI and reported by NULL. The snapshot's cpu_hot flag is 1 only for an available raw CPU temperature strictly above 80000 millidegrees Celsius, independent of display rounding; when set, CPU is the first metric. Rust and the native adapter must be built together against the current snapshot layout. C applies a red Pango foreground attribute only to that first metric's UTF-8 byte range in either layout. It replaces the attributes on every repaint, resetting color at or below 80°C, on missing CPU, or on collection failure. Other metrics retain normal color. This structured flag avoids reparsing rounded text; Pango attributes preserve plain-text label APIs, so scripts cannot inject markup.

monitor_fan_step takes unsigned integer off/auto temperatures in °C with 30 <= off < auto <= 90; the adapter and Rust must be rebuilt together against this signature. It returns an owned MonitorFanResult (status string plus a failed flag) released exactly once with monitor_fan_result_free; NULL represents a contained panic, which the adapter treats as a failed check before retrying. The failed flag drives the popup error area without parsing status text.

monitor_fan_level_read takes no arguments and returns an owned MonitorFanLevel (display text, tooltip, and failed flag) released exactly once with monitor_fan_level_free; NULL represents a contained panic, which the adapter displays as `?` with an observation-failed diagnostic before retrying. Text is `0`–`7`, `auto`, or `?`; failed is 1 exactly when text is `?`. It performs a read-only filesystem observation with no configuration, commands, or hardware writes. The adapter and Rust must be rebuilt together against this layout.

The GTK main loop launches one metric GTask at a time and schedules the next one-shot timer after completion. Its interval is a post-collection delay, not a wall-clock guarantee. A task holds state and plugin references; removal marks state removed, removes all timers, and prevents later widget access. Teardown waits on a condition signaled by each worker after Rust returns, independent of GTK callback dispatch, for metric collection, smart fan control, and fan-level observation. Retaining objects or mapping the module does not keep XFCE's external wrapper process alive: waiting is necessary to finish script cleanup before wrapper exit. Sequential timeout budgets may delay removal by up to 160 seconds plus collection overhead. Kernel filesystem/device I/O is not bounded.

Rust is linked PIC into the external module. Linux nodelete linking keeps worker/callback code and Rust TLS mapped if the module is closed while references remain. No system installation or panel restart is performed during development automatically.

## Verification boundary

Rust fixtures, subprocess failure tests, live CLI collection, release static-library builds, and a linked C ABI smoke test exercise the core. Native compilation and dynamic loading are verified on XFCE 4.20.7 / GTK 3.24.52. An isolated GTK harness with transparent native host/popup windows invokes the exported plugin factory and tests asynchronous readings, literal text, config reload, injected mode/orientation callbacks, and teardown during an extension timeout; its descendant must not write a delayed marker after removal. The harness isolates XDG configuration before GTK initialization and uses deadlines plus a global watchdog. A separately linked test-only fan backend verifies toggle defaults/visibility, asynchronous enable, retries during slow metrics and long refresh delays, rapid off/on serialization, stale-result suppression, and worker teardown. It never invokes sudo or changes fan hardware; Rust fan tests use temporary files and injected command writers. Fan-level fixtures cover documented values, missing/duplicate/malformed data, unsupported documented states, read errors, and tooltip diagnostics; the C ABI smoke test checks result ownership. The same test module links a read-only level backend to verify the bare display, `?` diagnostics without control fallback, one observation in flight, updates during RAM-only and stalled-metric/disabled-control conditions, and teardown with an active read. Popup coverage verifies bounds, live job snapshots, independent persistence, malformed files, save failures, error-area show/clear on fan failure, recovery and disable, and open-popup teardown with default and disabled animations. Escape coverage emits the GTK key-press signal; physical keyboard/outside-click routing remains a live-panel check. The host uses native windows because XFCE popup positioning needs native window origins; existing assertions remain in force. An additional X11 test embeds the plugin in a GtkPlug under a separate-process GtkSocket host and asserts that mapped sliders extend beyond panel height in an independent native toplevel. Separate processes are essential: GTK optimizes same-process XEmbed into widget reparenting, which would miss the clipping boundary. Staged installation is verified. Real fan writes, sudo authorization, actual panel discovery, the external wrapper process, and live-panel orientation remain unverified: callback injection and the isolated XEmbed host do not exercise all actual panel integration paths. README.md contains the remaining manual native verification checklist.
